## 2. 高频面试题与参考答案

### 2.1 基础概念题

**Q: 什么是 LLM？它的局限性是什么？**

> LLM（Large Language Model）是基于 Transformer 架构的大规模语言模型，通过海量文本数据训练，能理解和生成自然语言。
>
> 核心局限：
> - **知识截止**：训练数据有时间边界，不知道最新信息
> - **幻觉**：会生成看似合理但错误的内容
> - **无法访问私有数据**：不知道企业内部信息
> - **推理能力有限**：复杂逻辑和数学计算容易出错
> - **输出不确定**：同样输入可能得到不同输出
>
> 这些局限正是 RAG、Agent、结构化输出等技术存在的原因。

**Q: 什么是 Token？为什么重要？**

> Token 是 LLM 处理文本的基本单位。英文大约 1 token ≈ 4 个字符，中文大约 1 token ≈ 1-2 个汉字。
>
> 重要性：
> - **计费依据**：API 按 token 数量计费
> - **上下文限制**：模型有最大 token 限制（如 128K）
> - **性能影响**：token 越多，响应越慢、成本越高
>
> 实际应用中需要控制 token 使用：精简 prompt、压缩对话历史、分块处理长文档。

**Q: Temperature 参数的作用是什么？**

> Temperature 控制 LLM 输出的随机性，范围通常 0-2：
> - **0**：输出最确定，适合事实性任务（分类、提取）
> - **0.7**：平衡创造性和准确性，通用场景
> - **1.0+**：输出更随机有创意，适合头脑风暴、写作
>
> 前端类比：类似 CSS 的 `random-seed`，值越高结果越多样。

**Q: 什么是 Prompt Engineering？有哪些常用技巧？**

> Prompt Engineering 是设计和优化发送给 LLM 的指令，以获得更好的输出。
>
> 常用技巧：
> 1. **角色设定**：`你是一个资深的前端工程师...`
> 2. **Few-shot**：给出输入输出示例
> 3. **Chain-of-Thought**：`请一步步思考...`
> 4. **结构化输出**：指定输出 JSON 格式
> 5. **约束条件**：明确限制和要求
> 6. **分步指令**：复杂任务拆分为多步

### 2.2 RAG 相关题

**Q: 什么是 RAG？为什么需要它？**

> RAG（Retrieval-Augmented Generation）= 检索增强生成。
>
> 核心问题：LLM 只知道训练数据中的内容，无法回答关于私有数据的问题（如公司文档、内部知识库）。
>
> RAG 的解决方案：
> 1. 用户提问时，先从知识库中检索相关文档
> 2. 把检索到的文档作为上下文，连同问题一起发给 LLM
> 3. LLM 基于上下文生成准确回答
>
> 好处：不需要微调模型，知识可实时更新，成本低。

**Q: RAG 的文档分块策略有哪些？如何选择？**

> 常见分块策略：
> - **固定大小分块**：按字符数切分，简单但可能切断语义
> - **递归分块**：按段落、句子递归切分，保持语义完整
> - **语义分块**：基于 embedding 相似度切分，效果最好但成本高
> - **按文档结构分块**：按标题、章节切分，适合结构化文档
>
> 选择建议：
> - 通用场景：递归分块（chunk_size=1000, overlap=200）
> - 技术文档：按文档结构分块
> - 对话记录：按会话分块

**Q: 如何评估 RAG 系统的效果？**

> 评估维度：
> 1. **检索质量**：检索到的文档是否相关（Recall@K, MRR）
> 2. **生成质量**：回答是否准确、完整（人工评估、LLM 评估）
> 3. **端到端效果**：最终回答是否满足用户需求
>
> 优化方向：
> - 检索优化：混合搜索（向量+关键词）、重排序（Reranking）
> - 分块优化：调整 chunk_size、overlap
> - Prompt 优化：更好的上下文利用指令

### 2.3 Agent 相关题

**Q: 什么是 AI Agent？和普通 Chatbot 有什么区别？**

> Chatbot：用户输入 → LLM → 输出，是一次性的问答。
>
> Agent：给定目标 → LLM 规划 → 选择工具执行 → 观察结果 → 继续或结束，是一个自主循环。
>
> 核心区别：
> - **自主性**：Agent 能自主决定下一步做什么
> - **工具使用**：Agent 能调用外部工具（API、代码执行、文件操作）
> - **循环推理**：Agent 能根据中间结果调整策略
> - **目标导向**：Agent 追踪目标完成进度

**Q: Function Calling 的完整流程是什么？**

> 1. 定义工具：用 JSON Schema 描述函数名、参数、用途
> 2. 发送请求：把工具定义和用户消息一起发给 LLM
> 3. LLM 决策：LLM 返回要调用的函数名和参数
> 4. 执行函数：你的代码实际执行这个函数
> 5. 返回结果：把函数执行结果发回 LLM
> 6. 最终回答：LLM 基于结果生成最终回复
>
> 关键点：LLM 不直接执行任何操作，它只是"建议"调用哪个函数。实际执行权在你的代码手中，这保证了安全性。

**Q: Agent 的 Memory 机制怎么设计？**

> 三层记忆设计：
>
> 1. **短期记忆（对话历史）**
>    - 当前会话的所有消息
>    - 实现：messages 数组
>    - 问题：token 限制，需要截断或压缩
>
> 2. **工作记忆（任务状态）**
>    - 当前任务的中间结果、待办事项
>    - 实现：Agent 的 state 对象
>    - 生命周期：任务级别
>
> 3. **长期记忆（持久化）**
>    - 历史对话摘要、用户偏好
>    - 实现：向量数据库存储
>    - 跨会话保留
>
> 压缩策略：
> - 滑动窗口：只保留最近 N 条消息
> - 摘要压缩：定期总结历史对话
> - 重要性过滤：只保留关键信息

**Q: 如何保证 Agent 的安全性？**

> 多层安全策略：
>
> 1. **工具白名单**：只暴露必要的工具
> 2. **参数校验**：验证 LLM 返回的参数（防注入）
> 3. **权限控制**：不同工具不同权限级别
> 4. **人工确认**：敏感操作前要求用户确认
> 5. **执行沙箱**：代码执行在沙箱环境中
> 6. **速率限制**：限制工具调用频率
> 7. **日志审计**：记录所有工具调用

### 2.4 系统设计题

**Q: 设计一个企业知识库问答系统**

> ```
> 架构设计：
>
> 前端层：
>   - Next.js + React
>   - 流式对话 UI
>   - 文档管理界面
>   - 来源引用展示
>
> API 层：
>   - /api/chat → 对话接口
>   - /api/docs → 文档管理
>   - 流式响应 (SSE)
>
> Agent 层：
>   - LangGraph Agent
>   - 工具：知识库检索、网页搜索、计算器
>   - 记忆管理
>
> RAG 层：
>   - 文档加载 → 分块 → Embedding → 向量数据库
>   - 检索 → 重排序 → 上下文拼接
>
> 存储层：
>   - 向量数据库（Pinecone/Chroma）
>   - 关系数据库（用户、对话历史）
>   - 文件存储（原始文档）
>
> 关键决策：
> - Embedding 模型选择（成本 vs 精度）
> - 分块策略（文档类型决定）
> - 检索策略（向量+关键词混合）
> - 对话历史压缩（token 控制）
> ```

**Q: 如何控制 AI 应用的成本？**

> 多层成本优化：
>
> 1. **模型分层**
>    - 简单任务用小模型（GPT-4o-mini）
>    - 复杂任务用大模型（GPT-4o）
>    - 路由逻辑决定用哪个模型
>
> 2. **缓存策略**
>    - Prompt 缓存（相同前缀复用）
>    - 结果缓存（相同查询复用）
>    - Embedding 缓存
>
> 3. **Token 优化**
>    - 精简 System Prompt
>    - 压缩对话历史
>    - 控制 max_tokens
>
> 4. **架构优化**
>    - 减少不必要的 LLM 调用
>    - 用规则引擎处理简单场景
>    - 批量处理而非逐条处理

### 2.5 前端相关追问

**Q: 前端开发者做 AI 应用有什么优势？**

> 1. **API 对接能力强**：LLM 就是 API，前端开发者天然擅长
> 2. **流式交互经验**：SSE/WebSocket 是前端的老朋友
> 3. **UI/UX 设计能力**：AI 应用最缺好的交互设计
> 4. **状态管理经验**：对话状态、Agent 状态类似前端状态管理
> 5. **全栈能力**：Next.js 等框架让前端能独立完成全栈 AI 应用
> 6. **工程化思维**：构建、测试、部署的工程能力

**Q: AI 应用的前端有什么特殊的挑战？**

> 1. **流式渲染**：逐字输出需要特殊处理，不能用普通请求
> 2. **Markdown 渲染**：AI 输出包含 Markdown、代码块、表格
> 3. **长内容处理**：对话可能很长，需要虚拟滚动
> 4. **加载状态**：AI 响应慢，需要良好的 loading 体验
> 5. **错误重试**：API 可能超时或限流，需要重试机制
> 6. **Token 显示**：用户想看到 token 消耗和成本

>
> **架构**：Next.js + Vercel AI SDK + LangChain + Pinecone + PostgreSQL
>
> **我的角色**：负责前端开发和 RAG 模块实现

> **技术难点**：
> 1. 检索准确率不够 → 引入混合搜索（向量+关键词），准确率提升 30%

> 3. 流式响应在弱网下卡顿 → 实现断点续传和 loading 状态优化
